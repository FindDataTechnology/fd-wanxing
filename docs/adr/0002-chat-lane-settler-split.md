# ADR-0002: 对话车道的调用者/结算方分离

日期：2026-10-09
状态：已接受（随 add-agent-chat-lane）

## 背景

平台计费公理（paas ADR-0014，隨门面抽取继承）是 caller-pays：API 车道上每个外部调用者持自己的 sub2api 键，探活即计费门，回合按分钟结算给调用者的键。这条公理对程序调用者成立且运转良好。

引入对话车道（浏览器里登录即聊的人类访客）后它不再自足：访客不持键。有三种出路——

1. **访客自动开户**（登录即 provision sub2api 账户 + 服务端铸键，caller-pays 原样延伸到人类）；
2. **主人全额承担**（访客免费聊，agent 主人开预算池兜底，GPT 商店形状）；
3. **混合瀑布**（平台补贴垫基线 → 主人池延长 → 耗尽后自带键续聊）。

## 决策

采 **3（混合瀑布）**，并把账本结构升为一等概念：**调用者（Caller）与结算方（Settler）分离**。每笔回合记账同时记「谁发起」与「谁买单」——API 车道两者恒等（访客键=结算键，行为零变化）；对话车道上结算方 ∈ {平台补贴, 主人池, 访客自带键}，由准入时的瀑布判定。

配套决定：

- 计量单位沿用**分钟**（结算/预算/账本全链路同单位；A2A 响应不含 token 用量，且 agent 回合的真实成本在运行槽时长而非 token 产出）。
- 平台补贴是**获客成本不是访客权利**：全局开关 + 每访客每日限额，随时可关。
- 主人池是**放行上限不是储值**：实扣部署者的计费键（经 packs internal 结算契约，键值不出謙面），超支照记不丟账。
- 访客身份走共享 tenant（验 ID token、不查名单）；注册开放是 tenant 现状，console 允许名单继续独占管理面。

## 后果

- 正面：漏斗零摩擦（补贴段）、主人可运营自己的获客成本（池段）、大用户自然过渡为键持有者（桥段）；API 车道与其计费公理完全不动。
- 负面：门面准入与结算各多一个分支（settler 判定/两条结算路径）；免费面存在被批量注册薅补贴的风险（以独立更紧限流 + 每日分钟封顶压住，接受残余）。
- 未选路线的回归口：若未来补贴滥用失控，可全局关补贴退化为「仅主人池」；若访客自动开户被验证为需求，瀑布第三级自然升级为 provision 流——本结构不与之冲突。

## 与既有决策的关系

- 修订 ADR-0014 caller-pays 的适用范围：由「全部外部流量」收窄为「API 车道」；对话车道以结算方瀑布补足公理。
